# trace-lab-research

TRACE-LAB: a reproducible, versioned method for triaging field-level data
anomalies in laboratory information pipelines by combining anomaly detection
with versioned data lineage and a frozen defect-category dictionary.

The repository contains the full method (P2 scope): a deterministic synthetic
data generator, five-table data validation, anomaly detection, versioned
lineage resolution, transparent rule scoring, triage decisions, four
comparison baselines, and a held-out perturbation evaluation harness.

## Data scope statement

All data in this repository is synthetic (program-generated). The data
tables consist of synthetic case records for method demonstration and
reproducibility, generated by a seeded, deterministic generator. No
individual-level data appears anywhere in the repository, in any file, in
any branch of history. The field names, systems, node identifiers, and
change register are fictional.

## Five data tables

| Table | Role |
| --- | --- |
| `lineage_nodes` | 32 nodes across `SCHEMA_V1` (valid through 2025-06-01; 24 of 32 nodes close at the boundary and eight long-lived fields stay open-ended) and `SCHEMA_V2` (from 2025-06-01), each with `valid_from`/`valid_to` |
| `lineage_edges` | 40 edges with the same version validity semantics |
| `schema_changes` | change register (defect changes + normal-change negative controls) |
| `field_profiles` | per-field datatype, allowed range, unit, missing-rate profile |
| `field_observations` | 2020-observation stream with deterministic noise |

Ground-truth files (`defect_tickets.csv`, `perturbation_library.json`,
`normal_control_index.csv`) exist only for the held-out evaluation harness.
Triage never reads them; a leakage test proves outputs are byte-identical
without them.

## Defect category dictionary (frozen)

`UNIT_CHANGE`, `INTERFACE_MAPPING_ERROR`, `FIELD_SEMANTIC_CHANGE`,
`EXTRACTION_FAILURE`, `TRUE_BUSINESS_CHANGE`, `UNKNOWN`.

Precedence rules (e.g. `UNIT_CHANGE` precedes `INTERFACE_MAPPING_ERROR`) and
exclusivity rules (e.g. `TRUE_BUSINESS_CHANGE` excludes every defect
category) are encoded in `configs/p2_categories.yaml` and applied between
candidates, never between tickets.

## Decisions

Every anomaly window resolves to `TRIAGE` (advisory human review with cited
candidates and scores) or `ABSTAIN` with exactly one reason code:

- `AMBIGUOUS_CANDIDATES` — near-coincident changes with overlapping effective
  windows and scores within the tie threshold
- `LINEAGE_UNRESOLVED` — the upstream lineage at the anomaly time is broken,
  cyclic, or contradictory
- `INSUFFICIENT_EVIDENCE` — no candidate passes both required gates (lineage
  path association and time validity), or the best score is below the
  triage threshold

`TRIAGE` recommends human review; it does not assert causation.

## Quick start

```
uv venv venv --python 3.12
uv pip install --python venv/bin/python3 -e .
venv/bin/trace-lab generate-synthetic --output synthetic_data/ --seed 20250110
venv/bin/trace-lab validate --input synthetic_data/ --out outputs/runs/p2_validate/
venv/bin/trace-lab p2 triage --input synthetic_data/ --out outputs/runs/p2_triage/
venv/bin/trace-lab p2 evaluate --run outputs/runs/p2_triage/ --out outputs/runs/p2_evaluation/
venv/bin/trace-lab manifest inspect --run outputs/runs/p2_triage/
venv/bin/python3 -m pytest tests/
```

See `docs/USAGE_GUIDE.md` for details and `docs/frozen_metrics.md` for the
locked-in evaluation results.

## Reproducibility

- Deterministic generator (seed 20250110); two generations are byte-identical.
- SHA-256 hashes over canonicalized content; manifests carry `config_hash`,
  `data_hash`, `results_hash`, and a derived `result_hash`.
- Run ids, timestamps, and hashes are deterministic: re-running the
  documented commands reproduces the committed artifacts byte-for-byte.
- A re-computation test runs the full pipeline twice and compares every
  artifact byte-for-byte.

## Non-goals

This repository shows and stress-tests the method on generated data.
It does not contain real case data, does not make clinical or legal claims,
and its metrics describe method behavior on the generated dataset only.
External validation on real records is future work (`external/`).
